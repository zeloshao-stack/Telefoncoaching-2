## Phase 3 — A05 Fünf Schema/API-Steals

Nicht I1–I8, nicht J1–J8. Jeder Steal: 010-Quelle → Vertrag → Nicht. Evidenz **PLAUSIBEL** außer HEAD-Fakten.

### S1 — `call_moments`: `moment_t` + `quote` als eigene Zeile (Gong POI)

**Quelle:** 010-Gong E.1 / Help Call-Page: Points of Interest auf der Timeline, Klick = Sprung; API-Spiegel `pointsOfInterest` (010 Q60, PLAUSIBEL). Snippet = denselben Moment wiederholen, nicht Library. 010-Hyperbound E.8 Objections-Tab: Timestamp + Zitat nach Stop. Careertrainer: eine Stärke + ein Fix + Anker.

**HEAD:** `KeyMoment { turnId, quote, … }` nur im `evaluation_json`. `turns` hat `seq` und `created_at`, keine call-relative Uhr. Repeat hängt an `importantMomentTurnId`.

**Vertrag:**

| Feld | Pflicht | Semantik |
|---|---|---|
| `moment_id` | ja, zufällig | Zeilen-ID, **kein** Bearer |
| `session_id` | ja = Token | Capability der Sitzung, nicht exportieren |
| `turn_id` / `turn_seq` | seq ja | Gesprächsordnung bleibt `turns.seq` |
| `t_ms` | nullable | Offset **ab Gesprächsbeginn in ms**. `NULL` = unknown — **keine** Wanduhr-Delta-Erfindung aus `created_at` |
| `quote` | ja | wörtliches, kurzes Zitat |
| `speaker` | ja | `trainee` \| `counterpart` |
| `kind` | ja | Gate A: `key` \| `strength` (Einwand später) |

Schreiben: **nur** derselbe Post-Call-Job, der die eine `evaluations`-Zeile legt (008-J2 Unique ist Voraussetzung; S1 nicht allein bauen). Unique `(session_id, kind)` für `key` und `strength`. Replay = No-Op. Override (`purpose=trainee_override`) ersetzt, stapelt nicht.

Lesen: nur Debrief (`GET …/evaluation` nach `analyzed`). Live-GET: leere Liste, Feld weglassen. Sprung: `t_ms` wenn gesetzt, sonst `turn_seq` — keine Gong-Timeline-Behauptung ohne Aufnahme-Uhr.

Delete: mit Session/Turns/evaluations; sonst Zitat-Rest (HEAD-Recording-Fehler).

`moment_id` allein berechtigt nichts. Zugriff immer `session_id` (Token) + `moment_id`.

Nicht: Gong-POI-Taxonomie (Preis/Wettbewerb/Filler) als Note. Nicht Talk-Ratio. Nicht Live-Marker. Nicht `t_ms = created_at - session.created_at`.

### S2 — Scorecard-Projektion auf `evaluations`, kein zweiter Store (Hyperbound Scorecard-Objekt)

**Quelle:** 010-Hyperbound: Scorecard ist **eigenes Objekt, nicht Bot-Brain**; Note nach Stop; Kriterium → Begründung + Transkriptzitat; Preview vor dem Wählen lehrt auf den Test (AVOID). Careertrainer Dual-AI: zweite KI nach dem Gespräch, nur Trainee-Formulierungen.

**HEAD:** `evaluations(id, session_id, evaluation_json, created_at)` — Isolation vom Role Player ist da; Querybarkeit und Lebenszyklus nicht. `toDto` hängt die Note an jedes SessionDTO. Hangup schreibt die Zeile synchron.

**Vertrag:** Keine Tabelle `scorecard_results`. Eine Note bleibt **eine** `evaluations`-Zeile (008-J2 Unique, nicht neu). Neu ist die **API-Projektion**, die Board und Debrief brauchen, ohne Blob-Parse und ohne Live-Mitgabe:

```text
ScorecardView {
  session_id,          // Token, nur mit Capability
  state,               // queued | skipped_drop | skipped_mutated | analyzed
  focus_id,
  score,               // number | null (N/A / not_assessable)
  quote,               // Beleg, Speaker trainee bevorzugt
  moment_id,           // Zeiger auf S1 kind=key, darf fehlen bis analyzed
  analyzed_at | null
}
```

Regeln:

- `GET /api/sessions/:id` (Live): `evaluation` immer `null`, kein `ScorecardView`, keine Moments.
- `POST /api/sessions/:id/end`: schreibt **keine** `evaluations`-Zeile.
- Scorecard-Felder entstehen erst, wenn der Job auf `analyzed` fällt.
- Role Player, `state_json`, `character_json` sehen die Projektion nie.
- Drop / `mic_revoke`: kein Job, kein Score `0` (008-J6, hier nur angewendet).

Nicht: zweite Score-Tabelle. Nicht Scorecard-Preview im Briefing-API. Nicht Style/Filler als `score`. Nicht 70/30-Formel (010-Hyperbound: kein Beleg; Careertrainer nicht klonen).

### S3 — Hangup-HTTP ≠ Eval-HTTP (Score nach Auflegen, nicht im Realtime-Pfad)

**Quelle:** Gong Practice: Stop → erst dann Scorecard. Hyperbound Post-Call-Screen nach End. Careertrainer Examiner nach Auflegen. A00: keine Live-Noten. 008-J2/J6: Maschine schon beschrieben — hier der **HTTP-Schnitt**, den 011 braucht.

**HEAD (VERIFIZIERT):** `hangUp` → Tx `status=ended` → `await runEvaluation` → `reevaluateSession` INSERT. `POST …/end` gibt erst danach `SessionDTO` inkl. Note zurück. Kommentar in `lib/sessions.ts`: Client-Abort darf Eval nicht killen — der Await hält die Hangup-Antwort trotzdem.

**Vertrag:**

| Route | Nach Steal | Verboten |
|---|---|---|
| `POST /api/sessions/:id/end` | Tx: `ended` + `ended_reason`. Antwort `SessionEndedView` ohne Score/Moments. **Kein** `reevaluateSession` | Eval-Await, Score im 200 |
| `GET /api/sessions/:id` | Live-DTO, Token=id | `evaluation`, `moments` |
| `GET /api/sessions/:id/evaluation` | `404` unbekannt; `409` nicht ended; `202` queued; `200` analyzed + ScorecardView + moments[] + comparison | GET erzeugt Job oder Note |
| `POST /api/sessions/:id/evaluation` | Override-Job, Unique `trainee_override` | latest-wins-Stapel |

Enqueue des Jobs **nach** Commit, als Funktion von `ended_reason` (J6): `user_hangup` / gehörter `character_hangup` ja; `disconnect` / `mic_revoke` nein.

Idempotenz: zweites `POST /end` bei schon `ended` = dasselbe `SessionEndedView`, kein zweiter Job.

Nicht: Eval im `appendLiveTraineeTurn` / live-turn. Nicht Rubrik im Instruction-Patch.

### S4 — `board_column` abgeleitet, vier Übungs-Spalten (Gong-Board ohne Forecast)

**Quelle:** A00 widerlegt 010-Gong AVOID nur für „Verlauf als Deal-Board-Analog“. Gong-Forecast, 300+ Signale, Account-Boards, €, Commit: weiter AVOID. Hyperbound Manager-Dashboard / Leaderboard: AVOID (kein Team).

**HEAD:** `/verlauf` ist eine flache Karte; Badge „Ausgewertet“ bei jedem `ended`. Keine Spalte, kein `ended_reason`.

**Vertrag:** Spalte wird **nicht** persistiert (keine zweite Wahrheit neben `status` + Job). Ableitung:

| `board_column` | Wenn |
|---|---|
| `live` | `status=active` |
| `hung_up` | `ended` und Job fehlt / `queued` / `skipped_*` |
| `reviewed` | Job `analyzed` und kein Kind-Repeat gestartet |
| `repeat` | diese Zeile ist Elternteil einer anderen Session (`EXISTS child.parent_session_id = this.id`) |

Eine Session, eine Spalte. Eltern und Kind sind **zwei** Karten: Eltern `repeat`, Kind unabhängig `live` / `hung_up` / `reviewed`. Die offene Leitung bleibt die Kind-Karte in `live`. Kein `won` / `lost` / `commit` / `forecast` / Betrag / Close-Date / MEDDPICC.

`ended_reason` (006/008) bleibt Session-Feld für die Ableitung, nicht die Spaltenüberschrift.

Nicht: Revenue-Theater. Nicht Arbeitgeber-Board. Nicht Spalte als manuell ziehbarer CRM-Status.

### S5 — `SessionBoardRow` statt `SessionDTO`; Token bleibt `sessions.id`

**Quelle:** A11/007-I1: Session-ID = Token, kein zweites öffentliches Handle. Gong-Board zeigt Deal-Karten, nicht das volle Call-Dokument. Hyperbound Call History: Recording/Transcript/Score — bei uns nur nach Capability, Gate A ohne Team-Export.

**HEAD:** `listRecentSessions` → volle `SessionDTO` (Turns, Evaluation, `publicBrief`, Heard). Kein List-GET, aber `/verlauf` und `/gespraeche` ziehen dieselbe Hydrierung. `compareWithPrevious` liefert `previousSessionId` (= Token der anderen Sitzung).

**Vertrag:**

```text
SessionBoardRow {
  id,                    // Token = Bearer für den Link /sitzung/{id}/…
  scenario_id, scenario_title, counterpart_name, focus_id,
  board_column,          // S4
  ended_reason | null,
  created_at,
  parent_session_id | null,   // Herkunft, kein Nachladen der Leiche
  moment_quote | null,        // nur reviewed, aus S1 kind=key
  t_ms | null,
  score | null                // nur reviewed; null bleibt null
}
```

Verboten auf der Board-Projektion und auf jedem künftigen `GET`-Listenvertrag: `turns[]`, `character_json`, `hidden_facts`, `state_json`, `evaluation_json`, `live_call_id`, `heard[]`.

Server-intern darf `/verlauf` Turns weiter lesen (Patterns/`skillHistory`) — das ist kein List-Vertrag. Ein späteres JSON-List-API darf nicht `toDto` recyceln.

Token-Regeln:

- Kein `board_share_id`, kein `live_call_id` als Karten-Schlüssel.

- Logs/Usage/Ops: Token nicht im Klartext (007-I1/008-J3, nicht neu).

- `previousSessionId` in der Comparison ist ein zweites Token — nur an den Client, der das **aktuelle** Token schon hat; nicht ins Board, nicht in Logs.

Nicht: Token rotieren. Nicht RLS. Nicht List-API ohne Projection.
